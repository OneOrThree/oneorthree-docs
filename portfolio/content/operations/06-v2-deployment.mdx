## 발행 단위와 버전

서버 릴리스는 재사용 이미지를 포함한 네 서비스 digest 조합을 기록합니다. 서비스 변경 지문은 마지막 운영 성공 상태와 비교해 누적 변경을 놓치지 않습니다. Data 또는 Realtime 변경은 두 서비스를 함께 빌드하는 규칙이 있습니다.

V2 태그와 S3 버전 기록에서 가장 큰 patch를 1 올립니다. `release:major/minor/patch` 라벨은 V2 스크립트가 읽지 않습니다. 과거 V1 태그의 더 큰 숫자도 V2 계산에 합치지 않습니다.

서버 CD는 네 서비스를 Compose에 넘기고 이미지·env·라벨이 바뀐 서비스를 재생성합니다. Infra revision만 바뀌어도 Data는 `OBS_INFRA_REVISION` 값 때문에 재생성될 수 있습니다.

## Android 자동 게시

main 머지 → Android CI → `app-android-cd` → Play internal은 자동입니다. 프로덕션 출시는 Play 콘솔에서 사람이 승격합니다.

- CI의 `server-gate` 잡은 2026-11-02부터 실패해도 다음 단계로 갑니다(`continue-on-error`). 앱이 쓰지 않는 서버 변경에도 막혀 internal 게시가 밀렸기 때문입니다. 결과는 실행 요약의 경고로 봅니다.
- #1633(11-08)부터 CI의 일회용 서명 AAB는 Gradle이 출시 검사를 다시 돌리지 않습니다. 대신 CD가 원본 CI 같은 attempt에 서버 검사 결과가 있는지 확인하고, 누락·취소·생략이면 거부합니다.
- internal 게시 성공은 운영 서버 호환성 검사 통과가 아닙니다. 로컬 운영 빌드는 위 5단계 검사를 모두 거칩니다. 프로덕션 승격 전에 `server-gate` 결과를 직접 봅니다.
- 버전 이름은 Git 태그로 정합니다. 게시에 성공하면 CD가 `app-<버전>-android-<versionCode>` 태그를 달고, 메시지에 그때의 운영 서버 태그를 적습니다.

## DB 변경과 복구

마이그레이션 지문이 직전 성공과 다르면 기본으로 배포를 멈춥니다. DB 변경 릴리스는 명시적 `allow_migration`과 호환 계획을 필요로 하며 `rollback`과 함께 사용할 수 없습니다.

서버 적용 실패는 직전 이미지 조합으로 자동 복구를 시도하지만 이미 적용한 스키마를 되돌리지는 않습니다. Kafka·Redis는 자동 복구하지 않습니다. 배포는 성공했고 기록 job만 실패했다면 서버를 다시 배포하지 말고 기록 단계를 복구합니다.

Terraform 변경은 별도 plan 승인 절차입니다. 이 문서의 CD 설명을 Terraform apply 승인으로 사용하지 않습니다.

## 관측과 구 환경

11월 2일 구 dev·운영 서버와 V1 workflow 14개를 정리했습니다. 현행은 V2 workflow이며 공용 검사와 release 계약 검사는 유지됩니다.

운영 문서가 확인한 Datadog Agent health와 웹 화면의 실제 최신 로그·APM 수신은 다른 점검입니다. 개발 환경에는 Datadog Agent를 설치하지 않습니다. [시스템 구성](/spec/system-architecture)에서 호스트별 역할을 확인합니다. 앱 배포 성공 뒤의 관측 단계 실패는 경고로만 남으므로 성공 배지만으로 로그 수집을 판정하지 않습니다. [로그·추적 안내](/spec/logging-and-observability)에 설정 상태·수집 경로·조회 방법을 정리했습니다. 앱 크래시 수집과 심볼 문제는 [11월 앱 크래시와 진단 공백](/operations/07-november-app-crashes-and-diagnostics)에 있습니다.

AWS 부하 테스트 실행·재개와 부하용 데이터 생성은 금지합니다. 과거 실험의 재시험 제안은 현재 운영 작업 지시가 아닙니다. 위 운영 핵심 검사는 출시마다 임시 계정 1개·섬 1개로 조회 몇 건을 보내는 기능 확인이며 부하 시험이 아닙니다.
