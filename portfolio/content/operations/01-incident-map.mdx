## 현재 운영 문서

이 문서의 사례는 당시 장애 기록입니다. 현재 서버·Kafka·Redis·백오피스의 발행·배포·복구는 [V2 운영·배포](/operations/06-v2-deployment), 호스트와 공개 경로는 [시스템 아키텍처](/spec/system-architecture)를 따릅니다. 과거 사례의 서버 주소나 workflow를 현재 실행 절차로 사용하지 않습니다.

## 장애를 어떻게 알아보고 복구했는가

배포 성공·HTTP 200·테스트 초록만으로 서비스가 정상이라고 판정할 수 없었다. 아래 사례는 원문 티켓·워크플로·기존 연구 노트에서 **영향 범위 → 증거 → 원인 → 조치 → 검증과 남은 일**을 이어 읽는 진입점이다. prod 사고와 dev·CI 문제를 구분하며, 운영 호스트를 새로 실측한 보고서는 아니다.

| 사례 | 환경 | 핵심 판정 신호 |
| --- | --- | --- |
| 필수 시드 누락 | prod | 빈 배열 200·마스터 0행 |
| 마이그레이션 순서 역전 | dev | 502·Flyway 적용 이력 |
| 적용된 마이그레이션 수정 | dev | 기동 로그의 체크섬 불일치(V38) |
| 배포 성공 단절 | dev CI/CD | timeout 시점의 부팅 로그 |
| 리뷰 잡 미실행 | CI | 실제 요청 run의 cancelled |

### prod — 필수 마스터 데이터 누락

**영향·근거:** GROMO-910에서 Flyway V1~V15 success와 Hibernate validate가 통과했는데도 온보딩 직업·상점 등은 빈 배열 200, 직업 설정은 4xx였다. 마스터 데이터가 없어 5xx만으로는 서비스 이상을 검출하지 못했다.

**복구·남은 일:** dev 값을 수동 복사해 임시 복구했다. 원문은 시드 코드화와 빈 DB 검증을 근본 대책으로 남겼다. 후속 구현 완료와 복구 시각은 별도 확인이 필요하다. [사고 2 — 빈 배열 200](/research/migration-incidents#사고-2--에러-로그-없이-빈-배열-200-gromo-910) · [GROMO-910](https://romance.atlassian.net/browse/GROMO-910)

### dev — 전 경로 502와 CD 6연속 실패

**영향·근거:** GROMO-1050→1063→1065는 V21이 V20보다 53초 먼저 병합·배포된 사고다. 적용 이력에 V20이 빠져 Flyway validation이 앱 기동을 막았고, nginx는 전 경로에 502를 반환했다.

**복구·남은 일:** dev 전용 out-of-order로 기동을 회복한 뒤 이미 적용된 V20을 수정해 checksum mismatch가 발생했다. 수습 2회 실패까지 기록했다. 재배포 전 적용 이력·체크섬을 확인해야 한다. [사고 3 — 머지 순서 역전](/research/migration-incidents#사고-3--53초-차이가-만든-3연쇄-gromo-1050) · [GROMO-1050](https://romance.atlassian.net/browse/GROMO-1050)

### dev — 적용된 마이그레이션 수정으로 배포 차단

**영향·근거:** 2026-09-17 04:21(KST) 이후 main의 Dev CD가 전부 실패했다. 문서 경로 일괄 치환([PR #773](https://github.com/OneOrThree/phone/pull/773))이 이미 적용된 `V38`의 주석 한 줄을 바꿔 Flyway `validate`가 기동을 막았다. 체크섬은 DDL이 아니라 파일의 해시라 주석도 대상이다. 근거는 기동 로그의 `Migration checksum mismatch for migration version 38`과 [run 35168718059](https://github.com/OneOrThree/phone/actions/runs/35168718059)이다.

**복구·남은 일:** 주석을 원복해 파일을 바이트 단위로 되돌렸다([PR #779](https://github.com/OneOrThree/phone/pull/779)). 같은 PR이 `migration-immutable` 워크플로로 적용된 마이그레이션의 수정·삭제·개명을 CI에서 막았고, 그 가드가 base를 PR 생성 시점 SHA로 잡아 낸 오탐을 [PR #781](https://github.com/OneOrThree/phone/pull/781)이 정정했다. 사람이 지키던 규칙을 CI로 옮긴 사례다. [주석 한 줄이 dev 배포를 멈췄다](/operations/03-migration-checksum-dev-block) · [GROMO-1911](https://romance.atlassian.net/browse/GROMO-1911)

### dev CI/CD — 실배포 성공 단절

**영향·근거:** 최근 40회 중 성공 12회가 전부 7/24 이전이었다. 마지막 성공도 55초·12번째 시도였고, 실패 컷오프 때 앱은 에러 없이 Hibernate 초기화 중이었다.

**조치·남은 일:** PR #451에서 대기를 60→150초로, APM 부착 후 #524에서 300초로 조정했다. 준비되면 즉시 통과한다. 대기 상향은 진짜 장애 탐지도 늦추므로 readiness와 부팅 분포를 함께 봐야 한다. 복구율 수치는 원문에 없다. [CI/CD — 대기 창의 근거](/research/cicd-infra#724-이후-dev-배포-성공-0건) · [PR #451](https://github.com/OneOrThree/phone/pull/451)

### CI — Spot 러너의 리뷰 잡 미실행

**영향·근거:** GROMO-862 연계 사례에서 skipped 대부분은 정상 if 분기였다. 실제 요청 run은 Set up job에서 cancelled됐고 OAuth 사용 전에 종료돼 키 교체로 풀리지 않았다. 원문은 배정 러너 소멸을 근거로 Spot 선점을 원인으로 판정했다.

**대책·남은 일:** 대화형 잡만 hosted로 복귀하고 이벤트 분기를 고치는 방안을 제안했다. 당시 쿼터 리셋 후 적용 예정이었으나, 실제로는 2026-09-17 저장소 공개 전환(GROMO-1910 · [PR #778](https://github.com/OneOrThree/phone/pull/778))으로 한도 전제가 사라지고 GROMO-1918([PR #788](https://github.com/OneOrThree/phone/pull/788))이 GAR 의존 없는 잡을 전부 옮기면서 적용됐다 — 제안보다 범위가 넓다. **이벤트 분기 결함은 그대로 열려 있다**(`claude-review.yml`의 if가 여전히 `github.event.issue.pull_request`를 요구해 인라인 리뷰 요청은 항상 skipped). [Spot 러너 선점 사례](/operations/02-spot-runner-preemption) · [GitHub-hosted 이전](/research/ci-github-hosted-migration)

## 2026년 11월 V2 운영 사례(11-03~11-18)

### 앱 — Android 릴리스 크래시와 진단 공백

**영향·근거:** 카카오 SDK 토큰 확인 호출이 R8 full mode에서 제네릭 정보를 잃어 Android 운영 앱이 복귀 때 꺼졌습니다(GROMO-2740). 집중 준비 카드가 키보드가 뜰 때 높이 측정을 반복해 `Maximum update depth exceeded`로 꺼졌습니다(GROMO-2750, PR 기준 1명 3회). AI 측정 모델이 릴리스 번들의 리소스 이름 때문에 로드되지 않았습니다(GROMO-2751). Android 2.3.0·2.3.1은 Sentry 모듈이 없어 새 JS를 받으면 크래시 수집이 끊길 위험이 있었습니다(GROMO-2738).

**복구·재발 방지:** R8 규칙(#1579), 1px 미만 높이 변화 무시(#1590), Android 전용 캐시 파일 주소(#1591), Sentry 모듈이 없을 때 기존 PostHog 수집 유지(#1574). 디버그 빌드로는 재현되지 않아 dex 서명·소스맵·AAB 대조로 원인을 좁혔습니다. 상세: [11월 앱 크래시와 진단 공백](/operations/07-november-app-crashes-and-diagnostics)

### 앱 — OTA에 AI 판정 모델이 빠짐

**위험·근거:** #1658이 모델 파일을 바꿨는데 OTA 에셋 목록은 `src/assets/ota/**`만 실었습니다. 운영 env `expo export`에서 tflite가 0개였습니다. 그대로 OTA를 냈다면 기존 바이너리의 옛 모델만 남아 측정이 모델을 못 읽었습니다.

**조치:** OTA 에셋 목록에 `src/assets/ml/**`를 더했습니다(#1664, GROMO-2879). 수정 후 tflite 2개가 실렸습니다. OTA 받은 기기의 모델 로딩은 PR 단계에서 확인하지 않았습니다.

### 앱 — 카메라 작업 수명, 측정 불가 기기, iOS 메인 스레드

**영향·근거:** Android 2.3.25에서 카메라 작업 해제 중 네이티브 크래시(CATTUS-D), iOS 2.3.4 iPad 크래시(CATTUS-8)는 dSYM이 없어 해독하지 못했습니다. Vulkan 1.1이 없는 Android 기기는 판정 불가가 확정된 뒤에도 카메라를 20초마다 다시 켜고 `frame_timeout`을 계속 보냈습니다(GROMO-2899). iOS 2.3.7 iPad에서 실시간 현황 토큰 관찰이 메인 스레드를 2초 넘게 막았습니다(GROMO-2900).

**조치·남은 일:** 카메라 Worklets 패치·진단 수집·iOS dSYM 배포 차단(#1671), 판정 불가 세션의 주기 측정 중단(#1674), 토큰 관찰을 메인 스레드 밖으로(#1675). CATTUS-8 원인은 확정되지 않았고, dSYM 차단은 그 크래시의 수정이 아닙니다. 재발 여부는 수정 빌드 배포 뒤 판정합니다.

### 앱 — iOS 업데이트 편지의 스토어 버튼 404

**영향·근거:** iOS 2.3.0은 11월 3일 기존 App Store 앱(`com.oneorthree.gromo`)의 업데이트로 공개됐지만, 업데이트 편지의 iOS 버튼은 공개된 적 없는 다른 앱 ID를 가리켰습니다. iTunes lookup이 0건이었고 스토어 페이지는 404였습니다.

**조치·남은 일:** 링크·문서를 실제 앱으로 고쳤고(#1584), main iOS 프로젝트 번들도 바꿨습니다(#1586). 기존 사용자에게는 OTA나 다음 바이너리가 나가야 반영되며, iOS 최소 버전 게시는 그 뒤에 하도록 적었습니다. [V2 운영·배포 — iOS 번들 전환](/operations/06-v2-deployment#ios-번들-전환)

### prod — 퀘스트 만들기 503과 결정 없이 닫힌 스위치

**영향·근거:** 운영에서 섬장이 퀘스트 「+ 만들기」를 누르면 Data가 503 `QUEST_CREATION_UNAVAILABLE`로 거절했고, Business는 공개 400 「잠시 후 다시 시도해 주세요」로 바꾸며 ERROR 로그를 남겼습니다. 그 로그로 운영 ERROR 메일이 왔습니다. 원인은 GROMO-1773부터 `false`로 고정된 퀘스트 생성·정산 스위치였고, 이를 바꾼 결정 기록이 없었습니다.

**복구·재발 방지:** 스위치를 코드에서 지웠습니다(#1638, GROMO-2822). 같은 PR에서 relay·알림 발송·알림 Kafka 수신을 배포 프로필 기본 ON으로 바꿔, 설정 키가 빠져도 조용히 멈추지 않게 했습니다. 운영 반영은 2026-11-10 00:08 KST `catus-v2.0.11-V2`입니다. 실패 건수와 시작 시각은 원문에 없습니다. [ADR-040](/adr/adr-040-remove-launch-switches-default-on)

### prod — 잡지 자동 발행 중단

**영향·근거:** 10월 29일 콘텐츠 승인 백오피스(#1388)가 들어오면서 10분 주기 잡이 새 호를 자동으로 만들지 않고, 운영자가 검토·승인·게시해야 호가 생기는 구조가 됐습니다. 이 코드는 운영 V2 첫 태그(`catus-v2.0.0-V2`, 10-30)부터 들어 있었습니다. 백오피스 검토본이 없으면 그날 잡지가 발행되지 않았습니다. 실제로 빠진 날짜 수는 저장소에 없습니다.

**영향·근거:** 11월 10일 「건물을 지으려고 모으던 물고기와 친구 몫이 0이 됐다」는 문의가 1건 왔습니다. 당시 운영의 여러 건물은 주민별 할당(`RESIDENT_SPLIT`)으로 모금했고, 「각자 몫」은 현재 건설 목표 회차의 기여만 셌습니다. 섬장이 목표를 바꾸면(같은 건물을 다시 골라도) 회차가 바뀌어 모두 0부터 다시 셉니다. 섬 통장 잔액은 줄지 않았습니다. 목표 변경 확인창은 「모아 둔 물고기는 그대로 사용할 수 있어요」라고만 안내해 몫 초기화를 알리지 않았습니다.

**복구·재발 방지:** 소유자 결정으로 문의한 섬의 주민 2명에게 각 200마리를 보상했습니다(11-10, 섬 통장과 현재 회차 몫에 함께 반영, ROLLBACK 시험 뒤 반영). 대상은 문의자 확인 회신 전에 데이터로 추정했습니다. 규칙 자체는 #1642(GROMO-2761)가 모든 건물을 섬 통장 잔액 기준(`WALLET_TOTAL`, Data V14)으로 바꿔 없앴고, 11-11 04:08~04:12 KST `catus-v2.0.12-V2`로 운영에 반영됐습니다. 이 규칙에서는 같은 확인창 문구가 사실과 맞습니다. 보상 SQL·운영 조회는 저장소 밖 작업 기록이며, 이 페이지는 섬 이름·닉네임을 적지 않습니다.

## 운영 판단으로 이어진 변화

**서비스 정상성은 응답 내용과 DB 상태까지 본다.** 시드 누락은 빈 목록이 정상 200이라 상태 코드 기반 관측에서 빠졌다. 필수 데이터의 개수·불변식과 실제 사용 흐름을 검사해야 한다. 시드 코드화와 부팅 검증은 원문의 후속 대책이며 이 페이지에서 적용 완료로 바꾸지 않는다.

**앱 재배포와 DB 복구는 다른 작업이다.** 실패한 배포도 이미 DB를 바꿨을 수 있다. Flyway 적용 이력·체크섬·현재 이미지 SHA를 확인한 뒤 다음 조치를 정한다. 과거 파일을 고쳐 다시 배포하는 방식이 수습 실패를 늘린 이유는 [마이그레이션 기록](/research/migration-incidents)에 남겼다.

**원인은 실패한 단계와 시간 분포로 좁힌다.** 초기화 중 timeout, Set up job의 cancel, 실제 예외로 인한 기동 실패를 같은 “배포 안 됨”으로 취급하지 않는다. [관측 스택](/research/observability-evolution)과 [초록인데 깨진 사례](/research/green-but-broken)는 판정 신호의 사각지대를 연결한다.

**다음 경계는 켜기 전에 검증한다.** Kafka는 main 코드가 있어도 기본 OFF다. lag·DLT·oldest-pending·relay 실패율 기준선, 중복 재처리, Redis ACL·재구축의 운영 검증은 [현재 아키텍처](/spec/architecture)와 [회고](/retrospective/02-kafka-redis-boundaries)에 후속으로 남긴다. 장애 대응 경험과 아직 검증하지 않은 설계는 별도로 읽는다.

**닫힌 기능은 결정 기록과 함께 둔다(11월).** 퀘스트 503은 결정 없이 남은 `false` 스위치가 원인이었고, 잡지 미발행은 승인 단계를 넣으면서 자동 발행이 빠진 구조였다. 둘 다 오류가 아니라 「켜지지 않음」이라 늦게 드러났다. 스위치는 없애거나 배포 기본값을 켠 쪽으로 두고, 꺼 둔 기능은 티켓으로 따로 관리한다([ADR-040](/adr/adr-040-remove-launch-switches-default-on)).

**main 반영과 사용자 적용을 나눈다(11월).** 앱 수정은 새 바이너리나 OTA가 나가야 사용자에게 닿고, 서버 수정은 `prod-cd-V2`가 성공해야 운영에 있다. 크래시 재발 여부는 수정 빌드가 나간 뒤 같은 스택이 다시 오는지로 판정한다.
