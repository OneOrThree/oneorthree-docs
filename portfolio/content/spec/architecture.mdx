## 전체 연결

앱의 공개 HTTP 요청은 Business API가 받습니다. Business는 인증·입력·공개 응답을 정리하고 Data, Realtime, Notification의 내부 계약을 호출합니다. 웹소켓은 Realtime에 연결합니다.

| 서비스 | 소유하는 것 | 호출·전달 |
| --- | --- | --- |
| Business API | 공개 DTO·오류·화면 조합, 폐기 세션 확인 | Data·Realtime·Notification 내부 HTTP |
| Data API | 계정·주민 자격·섬·집중·물고기·편지·원장·outbox | PostgreSQL, Shared Redis presence, 사건 전달 |
| Realtime | 채팅 메시지 DB, 웹소켓 세션, 섬 이동 방 | Data 권한 조회, Shared Redis fanout·소유권 |
| Notification | 사건 수신·중복 방지·발송 이력·설정 | Kafka/내부 HTTP 수신, FCM 요청 |

[서비스 그림](/diagrams/03-service)과 [시스템 그림](/diagrams/04-system)은 같은 기준 커밋을 사용합니다. 과거 버전은 그림의 버전 선택에서 볼 수 있습니다.

## 정본과 재생 가능한 상태

제품의 최종 상태는 Data의 PostgreSQL에 있습니다. Realtime 채팅 DB와 Notification DB는 각각 자신의 도메인을 소유합니다. 서비스가 다른 서비스의 DB를 직접 조회하는 방식은 공개 계약이 아닙니다.

Redis는 공유 팬아웃, 집중 presence, 이동 소유권, 캐시, 폐기된 세션 판정에 쓰입니다. Redis Pub/Sub 메시지는 영속 로그가 아니며 놓친 사건은 재접속·스냅샷·HTTP 조회 등 각 기능의 복구 계약으로 다룹니다.

## 성공 응답과 후속 전달

Data의 상태 변경과 outbox를 같은 트랜잭션으로 기록하는 경로는 커밋된 사건을 나중에 다시 전달할 수 있습니다. 집중·휴식의 REALTIME 대상은 HTTP가 기본이고 Kafka는 별도 플래그로 선택합니다. 알림에는 Kafka 경로가 있습니다.

모든 작업이 하나의 트랜잭션인 것은 아닙니다. 섬 채팅은 Realtime에 먼저 저장·팬아웃한 뒤 Data의 `message.created` outbox를 별도 호출합니다. 후속 기록 실패를 이미 저장한 메시지의 롤백으로 설명하면 안 됩니다.

## 배포와 조건부 기능

운영 V2에서는 네 서버가 한 EC2에 있으며 Kafka·Redis·백오피스는 별도 EC2에 있습니다. 코드에서 경계를 나눴다는 사실과 서비스마다 호스트가 하나씩 있다는 주장은 다릅니다.

Realtime membership authorization, 차단 필터, Kafka 사건 소비는 독립된 설정입니다. 저장소 기본값이 OFF인 기능을 운영에서도 꺼져 있다고 단정하지 않습니다. 이동의 multi-instance 기능 기본값은 ON입니다. 실제 설정과 확인 범위는 [실시간 계약](/spec/messaging-and-realtime)에 모았습니다.
