## 도면과 기준

[시스템 도면](/diagrams/04-system)은 공개 요청 → 앱 호스트 → 저장소 → 관측 → 백오피스 → dev 순서로 읽습니다. 각 연결에 포트와 호출 주체를 표시했습니다. [로그·추적 도면](/diagrams/06-logging)은 수집기·보관소·요청 ID 연결을 확대합니다.

앱 코드는 phone `1281cbfc4`, 운영 구성은 GitHub 변수 `CATUS_PROD_INFRA_REVISION_V2`에 11월 4일 고정된 cattus-infra `69edca4d`를 대조했습니다. 11월 3일 기준(`8522746e`)에서 바뀐 것은 구 서버 Terraform 정리(#52)와 Data env의 Meta Conversions API 선택 키(#53)뿐입니다. Compose·nginx·보안 그룹·관측 설정은 그대로입니다. 호스트 목록·구 서버 종료·Agent health는 11월 2일 운영 기록을 따릅니다.

**설정에 존재하는 경로와 지금 운영에서 수신 중인 경로는 구분합니다.** 포트·보안 그룹 설명은 배포 설정 기준입니다. 이번 갱신에서 운영 호스트에 접속하거나 운영 API를 호출하지 않았습니다.

| 구성 | 운영 반영 상태 | 근거 종류 |
| --- | --- | --- |
| 서버 4종 | 릴리스 `catus-v2.0.14-V2`, 11-14 02:32 KST `prod-cd-V2` 성공. CD는 바뀐 서비스만 교체해 서비스별 운영 태그는 Data·Realtime v2.0.14, Business v2.0.13, Notification v2.0.11 | 운영 배포 기록 |

## 공개 요청이 서버에 도착하는 과정

`catus-api-v2.oneorthree.world` → Cloudflare 프록시 → 앱 EC2의 nginx `:443` → Docker `app-network`의 대상 컨테이너 순서입니다. nginx는 Origin 인증서로 TLS를 종료하며 `:80`은 HTTPS로 이동합니다. 이 경로에 ALB는 없습니다.

| nginx 경로 | 실제 대상 | 처리 |
| --- | --- | --- |
| `/auth/sessions`, `/me`, `/islands`, `/focus-sessions`, `/screens`, `/friends`, `/letters`, `/blocks`, `/customization` 등 공개 allowlist | `business-api:8080` | 공개 인증·DTO·화면 조합. 연결 2초·읽기 30초, 다른 upstream 자동 재시도 없음 |
| `/ws/realtime` | `realtime:8081` | WebSocket upgrade, 읽기 timeout 3600초 |
| `/l/<8자리 slug>` | nginx 고정 HTML | 초대 링크의 앱 열기·스토어 안내 |
| `/.well-known/apple-app-site-association`, `/.well-known/assetlinks.json` | nginx 고정 JSON | 앱 연결 파일 |
| `/static/customization/` | nginx 읽기 전용 static mount | 정적 꾸미기 자산 |
| `/internal`, `/internal/*`, `/actuator`, `/actuator/*` 및 나머지 경로 | 404 | 내부·관리·관측 API 공개 차단 |

경로 표는 주요 분기입니다. 정확한 허용 정규식은 [nginx 템플릿](https://github.com/OneOrThree/cattus-infra/blob/69edca4d5f9ef920a29cdba7f78dcca35e1be112/prod/catus-v2/runtime/nginx.conf-V2.template)이 정본입니다. 외부의 사용자·내부 호출자 헤더는 공개 프록시에서 제거합니다. 공개 HTTP로 들어온 우리 섬 채팅은 Business가 Realtime의 내부 REST로 전달하며, 현재 앱의 채팅 조회는 10초 폴링입니다.

11월 3일 이후 추가된 `POST /me/web-island`, `GET /islands/{id}/promotions/next`, `DELETE /islands/{id}/quests/{questId}`는 기존 `me`·`islands` 분기로 전달되어 nginx 변경이 필요 없습니다.

<Callout label="신고 경로 주의 · 코드 대조" tone="warn">

Business는 `POST /reports`를 공개하고(#1661, 운영 서버에 포함) phone의 dev·위성 nginx 예시는 `reports`를 허용 목록에 넣었습니다. 그러나 cattus-infra main의 운영 nginx 템플릿 허용 목록에는 `reports`가 없습니다. 코드대로라면 운영에서 이 경로는 마지막 `location /`의 404가 됩니다. 운영 요청으로 확인한 결과는 아닙니다.

</Callout>

## 앱 EC2 안의 컨테이너

`catus-prod-V2`는 `m6g.large` 한 대입니다. nginx와 네 JVM 서비스가 같은 EC2 자원을 공유합니다. 서비스별 코드·DB 소유권이 나뉘어 있어도 호스트 장애는 함께 영향을 줍니다.

| Compose 서비스 | 내부 포트 | 역할·연결 | 컨테이너 메모리 한도 |
| --- | --- | --- | --- |
| `business-api` | 8080, 관리 9091 | 공개 API → Data·Realtime·Notification 내부 HTTP. Business Redis 6380, DB 없음. 2KB 이상 JSON gzip | 2GiB, CPU 2 |
| `app` = Data API | 8080, 관리 9091 | 도메인 명령·권한·정산, 코어 DB·outbox·Shared Redis. 켠 경우 Meta Conversions API로 HTTPS | 1536MiB |
| `realtime` | 8081, 관리 9091 | 채팅 DB·WSS·이동, Shared Redis, Data 권한 조회 | 768MiB |
| `notification` | 8082, 관리 9091 | Kafka/내부 HTTP 사건 수신·발송 이력·알림 DB → FCM HTTPS | 768MiB |
| `datadog-agent` | APM 8126/TCP, DogStatsD 8125/UDP | Docker 로그·호스트 지표, JVM trace·runtime 지표, 앱 9091 OpenMetrics | 512MiB |
| `fluent-bit` | host network | Docker 로그 read-only tail → Loki·S3 | 256MiB, CPU 0.5 |
| `loki` | 호스트 **127.0.0.1:3100** | 별도 `observability` 네트워크, `loki_data:/loki` | 512MiB, CPU 0.5 |
| `grafana` | 공개 포트 없음 | Loki 조회 구성은 있지만 스위치 OFF | 활성화 시 256MiB |

8080·8081·8082·9091은 호스트의 공개 포트가 아닙니다. 서버 healthcheck와 Agent가 Docker 내부 주소를 사용합니다. Datadog의 OpenMetrics 목록은 Data의 Dockerfile 및 나머지 서비스의 Compose 라벨에 명시된 지표만 수집합니다.

Business는 read-only root, `cap_drop: ALL`, `no-new-privileges`를 적용합니다. 프로파일러용 `/ddprof`만 실행 가능한 tmpfs이고 일반 `/tmp`는 noexec입니다. 위 메모리 한도는 설정값이며 현재 사용량 측정치가 아닙니다.

Data는 `prod,satellites,realtime-authorization` 프로필로 뜹니다. `satellites` 프로필은 11-09(#1638)부터 relay를 기본으로 켭니다. Notification의 `prod` 프로필도 Kafka 수신과 예약 작업을 기본으로 켭니다. 같은 날 운영 비밀 저장소에도 세 값을 true로 명시했다는 기록이 있습니다.

## 서버에서 밖으로 나가는 연결

| 호출 주체 → 대상 | 프로토콜 | 켜짐 조건 |
| --- | --- | --- |
| Notification → FCM | HTTPS | 발송 게이트·예약 작업 |
| Data → Meta Conversions API | HTTPS | `META_CAPI_ENABLED=true`와 토큰. 코드·프로필 기본값 false. 운영 Data env 생성기는 11-04부터 이 키들을 선택 키로 전달(Infra #53) |

운영 비밀 저장소의 `META_CAPI_ENABLED` 실제 값은 이 문서에서 확인하지 않았습니다.

## 저장소와 호스트 간 연결

EC2는 기존 VPC의 public subnet을 사용하지만 서비스 간 통신 주소는 사설 IP입니다. 호스트마다 이름이 같은 `app-network`를 만들더라도 서로 다른 Docker 브리지입니다. Kafka·Redis 연결은 해당 EC2의 사설 IP에 publish한 포트로 나갑니다.

| 호출 주체 → 대상 | 호스트·포트 | 데이터·지속성 |
| --- | --- | --- |
| Data → 코어 DB | 기존 RDS `catus-prod-db:5432` | `gromo`: 제품 정본·원장·receipt·outbox·신고·첫 도착 사건 |
| Realtime → 채팅 DB | 같은 RDS:5432 | `gromo_chat`: 채팅 정본 |
| Notification → 알림 DB | 같은 RDS:5432 | `gromo_notification`: 수신·기기·설정·발송 이력 |
| Data relay → Kafka → Notification | `catus-kafka-prod-V2`, 사설 9092 | Kafka 3.8.1, broker/controller 1개·RF 1. `notification-events` 및 DLT, Realtime 소비는 별도 선택 경로 |
| Data·Realtime → Shared Redis | `catus-redis-prod-V2`, 사설 6379 → 컨테이너 6379 | presence·fanout·이동 소유권, maxmemory 384MiB |
| Business → Business Redis | 같은 Redis EC2, 사설 6380 → 별도 컨테이너 6379 | 폐기 세션 판정 등 전용 키, maxmemory 128MiB |

Kafka와 Redis EC2는 각각 `m6g.medium`입니다. Kafka는 `/var/lib/catus-V2/kafka`에 기록하고 controller 9093은 내부용입니다. 두 Redis는 `noeviction`·AOF·ACL을 사용하며 `/var/lib/catus-V2/redis-shared`와 `redis-business`를 각각 마운트합니다. 컨테이너 메모리 한도는 Shared 768MiB·Business 256MiB로 `maxmemory`와 다릅니다. Redis Pub/Sub은 AOF로 재생할 수 있는 사건 이력이 아닙니다.

운영 기록의 RDS는 `db.t4g.small`인 기존 **`catus-prod-db`**입니다. 별도로 만든 `catus-prod-db-v2`는 아직 미사용입니다. V2 Terraform의 새 RDS 정의만 보고 기존 DB가 전환됐다고 읽으면 안 됩니다.

## 보안 그룹과 관리 경로

| 수신 측 | 허용한 출발지·포트 | 용도 |
| --- | --- | --- |
| app·backoffice EC2 | Cloudflare IPv4 → 80/443 | 공개 웹 진입 |
| Kafka EC2 | app SG → 9092 | broker 연결 |
| Redis EC2 | app SG → 6379/6380 | Shared·Business 연결 |
| app EC2 관리 프록시 | backoffice SG → 18080/18082 | 내부 관리 API |

`catus-backoffice-prod-V2`는 `t4g.small` 별도 EC2입니다. `backoffice-v2.oneorthree.world` → Cloudflare → nginx:443 → `app:4310`으로 접속합니다. 로컬 상태는 `/var/lib/catus-V2/backoffice:/state`, 일일 백업은 별도 S3 버킷을 사용합니다.

백오피스의 Data·Notification 관리 호출은 앱 EC2의 사설 주소로 나갑니다. `backoffice-gateway` 컨테이너가 18080 → `app:8080`, 18082 → `notification:8082`를 전달합니다. 프록시는 정해진 `/internal/admin` 경로만 허용하고 서비스 인증 헤더를 전달합니다. 백오피스가 제품 DB에 직접 접속하는 경로가 아닙니다.

Data는 운영자 개인별 토큰(member-1~3)마다 관리 경로를 허용합니다. 11-09 이후 꾸미기 현황·추첨 풀·지급(2인 승인)과 11-12 신고 조회·종결 경로가 Data 허용 목록에 더해졌습니다. cattus-infra main의 gateway 허용 목록에는 이 경로들이 없습니다. 운영에서 백오피스 꾸미기 화면이 이 gateway를 거쳐 동작하는지는 이번에 확인하지 않았습니다.

구 `api`, `catus-api`, `focuscat-api`, `link` DNS는 11월 2일 삭제 기록이 있습니다. 구 `backoffice.oneorthree.world`는 V2 백오피스로 302 이동합니다.

| `try.oneorthree.world` 정적 파일 | Cloudflare 프록시 → Vercel `cattus-web-demo` | 3D 섬 웹(`app/metaverse-web`) |

11-07(#1623)부터 대표 주소의 웹을 3D 섬 웹으로 교체했습니다. 2026-11-19 대표 주소의 `version.json`은 소스 커밋 `919a49239`(#1629)와 위 실시간 방 주소를 가리켰습니다. 3D 웹은 운영 앱의 인증·계정·섬 통장·집중 기록과 연결하지 않고, 새로고침이나 연결 종료 때 방의 집중·예약을 해제합니다.

배포는 `metaverse-web-ci`가 검사만 하고, 소유자가 요청할 때 검증한 main 커밋으로 수동 배포합니다. AWS·앱 출시 워크플로와 분리돼 있습니다.

## 로깅이 실행되는 위치

앱 EC2에서는 Docker stdout 파일을 Datadog Agent와 Fluent Bit이 **각각** 읽습니다. Agent는 Datadog SaaS로 로그·APM·지표를 보내고, Fluent Bit은 허용한 네 서버·nginx 로그를 Loki와 S3로 나누어 전송합니다. Loki는 앱 EC2 디스크에 7일, S3 `system_log/v2/`는 90일 만료 규칙을 갖습니다. Grafana 스위치는 OFF입니다.

Kafka·Redis·백오피스 EC2는 각자의 Datadog Agent로 해당 호스트의 로그·지표를 수집합니다. 세 호스트에는 위 Fluent Bit→Loki·S3 경로가 없습니다. Data의 `user-activity.log`는 stdout 밖의 별도 파일이며, 11월 3일 확인한 호스트에는 업로더가 없었습니다.

로그 필드·마스킹·버퍼·유실 조건·조회 순서와 앱 오류 수집(Sentry)은 [로그·추적 안내](/spec/logging-and-observability)를 따릅니다. 11월 2일 네 Agent의 health PASS 기록은 Datadog·Loki·S3의 **최신 수신 확인**을 대신하지 않습니다.

## dev V2와 배포 소유권

| GCP VM | 사양 | 실행 대상 |
| --- | --- | --- |
| `catus-dev-v2-app` | e2-medium | nginx와 서버 4종 |
| `catus-dev-v2-data` | e2-small | PostgreSQL 16.14:5432와 Kafka 3.8.1:9092 |
| `catus-dev-v2-redis` | e2-micro | Shared·Business Redis 7.4.11:6379/6380 |

dev V2는 11월 5~6일 새 GCP 프로젝트로 옮겼습니다. 같은 서울 존에 같은 이름·사양의 VM을 만들고, 쓰기를 멈춘 뒤 PostgreSQL·Kafka·Redis·정적 파일을 복사해 해시를 대조했습니다. 공개 주소 `oneorthree-v2.dev.mooo.com`의 DNS도 새 주소로 바꿨습니다. main 변경은 관련 CI와 `cd-auto.dev-v2.yml`을 통해 자동 배포됩니다. dev 백오피스와 세 VM의 Datadog Agent는 없습니다. 과거 dev Prometheus·Grafana overlay를 V2의 가동 중 서비스로 표시하지 않습니다.

AWS 자원·SSM·서버/백오피스 Compose·env 계약은 `cattus-infra/prod/catus-v2/`, Kafka·Redis Compose는 phone `server/scripts/v2/prod/`가 소유합니다. 서버·Kafka·Redis는 release 발행 후 수동 CD, 백오피스는 main 머지 후 승인 배포입니다. [V2 배포 안내](/operations/06-v2-deployment)에 승격·마이그레이션·복구 제한을 정리했습니다.
