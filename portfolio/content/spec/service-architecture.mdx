## 공개 API와 내부 계약

Business는 앱의 공개 HTTP API와 `/screens/*` 조합 응답을 제공합니다. 화면에 필요한 조각을 내부 API에서 받아 공개 DTO로 옮깁니다. Data 엔티티나 내부 응답 DTO를 그대로 공개하지 않습니다.

Business는 2048바이트 이상인 `application/json` 응답을 gzip으로 보냅니다(#1569). 클라이언트가 gzip을 허용할 때만이며 작은 JSON과 이미지는 원본 그대로입니다. Realtime·Data의 직접 응답에는 적용되지 않습니다. 운영 앱의 전송량·지연 개선은 측정하지 않았습니다.

Data는 제품 권한과 원자 명령을 소유합니다. Business가 형식을 검사해도 주민 자격·섬장 권한·잔액·현재 세션 같은 최종 판정은 Data에서 이뤄집니다. 내부 호출에는 서비스별 토큰과 사용자 컨텍스트를 전달합니다.

## 데이터 소유권

| 데이터 | 정본 | 주요 주의점 |
| --- | --- | --- |
| 계정·섬·집중·물고기·건설·상품·친구·편지 | Data PostgreSQL | 원장·receipt·outbox와의 트랜잭션 경계. 건설은 주민별 분담 대신 섬 통장 잔액으로 짓는 방식으로 바뀜(V14) |
| 첫 섬 도착 사건 | Data `first_island_arrivals`(V10) | 계정당 1회. Meta 전송 상태를 함께 두고, 종료 상태가 되면 매칭 값을 지움 |
| 웹 전용 섬 배정 | Data `web_island_pools`(V11) | `POST /me/web-island`. 정원 검사에서 빠지는 섬 하나. 현재 공개 웹은 이 경로를 쓰지 않음 |
| 꾸미기 추첨 풀·지급 | Data(V12·V13) | 승인과 실행을 다른 운영자가 함 |
| 공지 대상 플랫폼 | Data(V15) | 앱이 보낸 플랫폼으로 개발자 소식을 거름 |
| 신고 | Data `safety_reports`(V16) | 신고자의 진술 기록. 위반 확정이 아님 |
| 우리 섬 채팅방 메시지 | Realtime PostgreSQL `gromo_chat` | `clientMessageId` 재전송 처리, REST 과거 조회, 탈퇴자 본문 파기(V4) |
| 알림 사건·발송 이력 | Notification PostgreSQL | 중복 수신과 외부 FCM 성공은 별도 |
| 집중 presence·이동·채팅 fanout | Shared Redis | 전송·표시 상태이며 제품 권한의 정본 아님 |
| 폐기 세션 | Business Redis | 기존 link-preview 캐시는 제거됨 |

V10~V16은 운영 Data(v2.0.14)에 들어 있습니다. 섬 퀘스트 soft delete인 V17(#1672)은 main에만 있습니다.

## 편지와 채팅

친구 편지는 공개 `/letters`를 거쳐 Data에 저장됩니다. 게스트 발송에는 `SOCIAL_LOGIN_REQUIRED`가 적용됩니다. 수신 목록과 상세 열람의 우체통 시설 판정은 호출자 측 섬 기준이며, 발송 시 상대 섬의 우체통 완공 여부를 검사하지 않습니다. 시스템 편지는 `kind=system`으로 구분합니다.

우리 섬 채팅방은 `/islands/{id}/messages`를 사용합니다. Business가 Data의 주민 자격을 확인한 뒤 Realtime 내부 REST를 호출합니다. 앱의 `useIslandChat`은 화면이 활성화되고 앱이 전경에 있을 때 10초마다 조회합니다. 서버에 legacy STOMP 채팅 경로가 남아 있어도 현재 앱의 단체 채팅이 그 경로를 구독한다고 설명하지 않습니다.

상세 권한·멱등성과 차단 규칙은 [편지·채팅·실시간 권한](/spec/messaging-and-realtime)에 있습니다.

## 신고

앱의 `POST /reports`는 Business를 거쳐 Data `POST /internal/users/{userId}/reports`로 갑니다(#1660·#1661). Business는 검증한 세션 정보를 본문과 분리해 넘기고, Data가 현재 세션을 다시 확인합니다. 같은 요청 키·같은 본문의 재시도는 같은 접수 번호를 돌려줍니다.

- 대상 종류: 사용자, 편지, 섬 채팅 메시지, 공지, 공지 댓글, 방명록, 섬, 기타.
- 접수는 자동 차단·자동 숨김을 하지 않습니다. 운영자가 실제 기록과 대조해 처리합니다.
- 운영 조회·종결은 Data의 관리 API(`/internal/admin/content/reports`)입니다. 백오피스 화면은 아직 없습니다.
- 종결 후 30일이 지난 일반 신고는 매시간 작업이 지웁니다. 법적 보존이 필요한 건만 사유와 함께 남깁니다.

공개 경로가 운영 nginx 허용 목록에 있는지는 [시스템 아키텍처](/spec/system-architecture)의 주의 사항을 봅니다.

## 운영 관리 API와 2인 승인

백오피스는 운영자 개인별 서비스 토큰(member-1~3)으로 Data 관리 API를 부릅니다. 요청한 운영자와 다른 운영자의 승인이 있어야 바뀌는 작업이 있습니다.

| 작업 | 흐름 | 추가 시점 |
| --- | --- | --- |
| 집중·황금 물고기 정책 | 승인 → 다른 운영자가 새 revision 발행 | 기존 |
| 꾸미기 추첨 풀 | 현황 조회 → 승인 → 다른 운영자가 새 revision 발행. 이전 풀은 영구 보존 | #1639 |
| 꾸미기 아이템 지급 | 대상 미리 계산(저장 없음) → 승인 → 다른 운영자가 실행 | #1641 |

지급 대상은 전체 또는 닉네임으로 고른 사용자입니다. 승인에는 닉네임이 아니라 사용자 UUID 스냅샷만 남깁니다. 실행은 사용자 한 명씩 트랜잭션을 나누고, 같은 지급 ID로 다시 부르면 이어서 처리합니다. 이미 실행에 쓴 승인은 취소할 수 없습니다.

## 사건 전달

Data relay는 대상별 전달과 재시도를 관리합니다. 배포 프로필에서는 11-09부터 기본으로 켜지며, 배치 크기·리스·재시도 간격에도 기본값이 있습니다(#1638). REALTIME 사건은 기본 HTTP, 선택적으로 `realtime-events`를 사용합니다. Notification의 Kafka 사건 경로는 `notification-events`를 사용합니다. 같은 사건의 HTTP·Kafka 수신도 소비자 중복 처리 계약을 따라야 합니다.

`auth.session.revoked`는 Notification뿐 아니라 Realtime에도 전달됩니다. Realtime은 폐기된 sid의 연결을 닫고 재전달을 막습니다. 연결 때 인증했다는 이유로 이후 세션 폐기를 무시하지 않습니다.

`user.withdrawn`도 Realtime에 전달됩니다. Data는 탈퇴 트랜잭션에서 송수신 편지를 지우고 이 사건을 기록합니다. Realtime은 사건을 처리할 때 해당 사용자의 메시지 본문·발신자·클라이언트 식별자를 지우고, 다른 사용자의 읽음 기준이 되는 행 ID와 순서만 남깁니다(#1659). 메시지 저장도 같은 사용자 잠금과 tombstone 검사를 거쳐 늦은 쓰기를 거절합니다.

## 이동과 재접속

이동 multi-instance 모드는 Redis의 섬 소유권 lease와 epoch로 소유 JVM을 정합니다. 다른 인스턴스의 명령은 소유자에게 전달되고, 프레임은 Redis를 거쳐 참여 인스턴스에 퍼집니다. 소유자는 자신이 만든 프레임도 같은 수신 경로로 처리합니다.

소유권을 잃으면 방을 비우고 발행을 중단합니다. 오래된 epoch 프레임은 무시하고 재입장 시 FullState를 받습니다. 정상 종료 handoff는 짧은 TTL의 Redis 좌표 인계이며 PostgreSQL에 모든 이동을 영구 기록하는 방식이 아닙니다.
