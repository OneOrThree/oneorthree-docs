## 현재 적용 범위

- 앱 측정은 iPhone 15 한 대에서 dev V2 서버와 시험 계정 하나로 했다. 운영 서버에 부하를 보내지 않았다.
- gzip 수치는 저장해 둔 응답 본문을 로컬에서 압축한 값이다. 운영 앱의 전송량·지연 개선 실측이 아니다.
- 반영 상태(저장소 기록 기준): #1576·#1577은 iOS 앱 태그 `app-2.3.1-ios-13`부터, 현재 iOS `app-2.3.7-ios-14`와 Android `app-2.3.26-android-906` 태그에 들어 있다. 스토어 공개 여부는 이 문서에서 확인하지 않았다. #1569는 서버 태그 `catus-v2.0.7-V2`부터 들어 있고, 운영 서버 `catus-v2.0.14-V2`(2026-11-14 운영 반영 기록)에도 포함된다.

## iPhone 15 측정 조건

- 기기: iPhone 15, iOS 27.0.1. 케이블을 꽂은 채(충전 중) 쟀다.
- 빌드: Release, Xcode 26.6, 개발용 서명(Instruments가 앱에 붙으려면 필요). 서버 dev V2, OTA 끔, PostHog 토큰 빈 값.
- 계정: dev V2 시험 계정 하나. 홈은 그 계정의 섬, 집중은 낚시섬에서 혼자.
- 기록: `xctrace record --attach`. 홈은 Hitches·Display·Time Profiler·Thermal State, 집중은 Time Profiler·Thermal State.
- 분석 구간: 홈 45초 조작, 집중 60초.
- 조작: 별도 XCUITest 러너가 정해진 동작만 눌렀다. 손가락 확대는 사람이 했다. 러너 소스는 저장소에 없어 같은 자동 조작을 문서만으로 재현할 수 없다.
- CPU는 앱 프로세스 기준이며 코어 하나를 꽉 채우면 100%다.

## 원인과 개선 전후

전후 비교는 2026-11-03 밤 main `b0940c786`을 기준으로, 그 위에 각 티켓의 커밋만 올려 쟀다. 위 오전 빌드 `239efc3f4`와 기준이 다르므로 전후 비교에는 아래 수치만 쓴다. 모두 60초, 케이블 연결 상태다.

### 집중 화면 메인 스레드 — 테두리 그림 다시 만들기 (GROMO-2736, #1576)

- Time Profiler에서 메인 스레드 시간의 53.0%가 `RCTGetBorderImage`(테두리를 그림으로 만드는 함수)였다.
- React Native iOS는 네 변이 같은 solid 테두리이고 두께 0·안쪽 잘라내기·투명 색 중 하나일 때만 Core Animation 테두리를 쓴다. 나머지는 테두리를 그림으로 만들고, 네이티브 드라이버가 opacity·크기를 바꿀 때마다 다시 만든다.
- 낚시섬 찌 주변의 물빛 반짝임 6개(윗변만 테두리)와 물결 고리 3개(안쪽을 잘라내지 않음)가 해당했다. 반짝임은 막대로 바꾸고 고리에는 `overflow: 'hidden'`을 줬다.

| 빌드 | 횟수 | 앱 CPU | 메인 스레드 | 메인 스레드 중 `RCTGetBorderImage` | 발열 상태 |
| --- | ---: | ---: | ---: | ---: | --- |
| 고치기 전 | 2 | 39.7% · 40.5% | 33.3% · 34.9% | 52.4% · 53.4% | Nominal · Fair |
| 반짝임만 막대로 | 1 | 28.2% | 22.9% | 32.6% | Nominal |
| 반짝임 + 물결 고리 `overflow: 'hidden'` | 3 | 18.6% · 18.4% · 18.6% | 13.6% · 13.5% · 13.5% | 0.3% · 0.3% · 0.3% | Fair |

- 원문 결론: 집중 화면 앱 CPU가 약 40%에서 18.5%로 절반 아래가 됐다. 홈 걷기(20.6%)와 비슷한 수준이다.
- 고친 빌드는 발열 상태가 Fair로 더 따뜻할 때 쟀는데도 낮게 나왔다.
- 처음에는 반짝임만 고쳤고, 다시 재 보니 메인 스레드의 33%가 아직 같은 함수여서 고리를 찾았다.
- 바꾸기 전후 낚시섬 집중 화면 캡처에서 달라진 곳은 없었다.

### 집중 전 카메라 미리보기 — 프레임 스레드의 JS 실행 (GROMO-2737, #1577)

- 프레임 스레드 시간의 85.3%가 JS 실행(`hermesvm`), 12.1%가 TFLite 등 앱 실행 파일이었다.
- 먼저 손 모델 입력 변환(192×192×3 = 110,592개 값을 0~1 실수로 바꾸는 일)을 원인으로 보고, 리사이저가 float32를 바로 내보내게 고쳤다.

| 빌드 | 횟수 | 앱 CPU | 프레임 스레드 중 `hermesvm` | 프레임 스레드 중 TFLite 등 |
| --- | ---: | ---: | ---: | ---: |
| 고치기 전 | 2 | 71.0% · 74.5% | 85.3% · 85.3% | 12.1% · 12.2% |
| 손 모델 입력 float32 | 2 | 71.0% · 75.1% | 84.1% · 84.4% | 13.3% · 13.0% |

- CPU 감소는 관측하지 못했다. 원문이 보는 가장 유력한 원인은 물체 모델 결과 검사다. 출력 19,206 위치 × 90 종류 = 1,728,540개 값을 모두 검사하지만 판정에 쓰는 것은 3종류(노트북·키보드·책)다. Time Profiler가 Hermes 안 함수 이름을 보여 주지 않아 반복 횟수로 본 추정이다.
- 미리보기는 집중 시작 전에 잠깐 켜는 화면이고, 집중 중에는 20초마다 3장을 판정한다. 주기 판정의 추가 비용은 이번 표본으로 확정하지 못했다.
- 고친 빌드에서 손과 노트북·키보드를 비추면 「집중 확인 완료」, 손을 빼면 「손이 보이지 않아요.」가 나왔다.

## 실기기 측정의 한계

- **배터리는 재지 않았다.** 케이블을 꽂아 충전 중이라 배터리 값이 0%/h로 나온다. 발열에도 충전 열이 섞였다.
- 표본이 적다. 홈은 장면당 3~5회, 집중은 1~2회다. 집중 8회 중 3회는 기록 도구가 앱에 붙지 못하거나 러너가 시작하지 못해 버렸다.
- AI 판정 캡처는 고친 빌드로만 찍었다.
- 지도 끌기·걷기는 합성 터치라 사람 손 속도와 다르다.
- 측정 바이너리의 해시와 원본 trace는 저장소에 없다.
- 남은 측정: 케이블을 뺀 30분 이상 배터리 소모, 홈 뗏목 물결(같은 테두리 구조 가능성), 물체 결과 검사 개선, 지도 끌기 27 fps 원인, Android 같은 장면.

## Business API 응답 gzip (GROMO-2734, #1569·#1571)

### 바뀐 것 (코드)

| 구분 | 적용 전 | #1569 병합 후 |
| --- | --- | --- |
| Business API 오리진 | HTTP 응답 압축 설정 없음 | Spring Boot 내장 응답 압축 |
| 압축 조건 | — | `Accept-Encoding`이 gzip 허용, `Content-Type`이 `application/json`, 원본 본문 2,048B 이상 |
| 작은 JSON·PNG | 원본 | 원본 |
| 압축된 응답 헤더 | — | `Content-Encoding: gzip`, `Vary: accept-encoding` |
| 앱까지의 전송 | Cloudflare 압축 여부 미확인 | Cloudflare를 거친 최종 인코딩·크기 확인 필요 |

Realtime의 HTTP·WebSocket 응답, Data API 직접 응답, 정적 이미지에는 이 설정이 적용되지 않는다.

### 어떤 응답이 대상인가 (2026-10-20 저장 표본)

10,000명 시험 fixture의 API preflight에서 200 응답의 원본 크기를 집계했다. 로컬에 보관한 자료다.

| 표본 범위 | 값 |
| --- | ---: |
| Business API 관측 행 / 서로 다른 경로 | 62행 / 56경로 |
| 200 응답 표본 | 186개, 합계 383,796B |
| 2,048B 이상 표본 | 60개(32.3%), 합계 340,987B(88.8%) |
| 2,048B 미만 표본 | 126개, 합계 42,809B |
| 한 번이라도 2,048B 이상인 경로 | 16경로 |

| 응답 예시 | 원본 크기 |
| --- | ---: |
| `/screens/mailbox` | 15,398–16,752B |
| 섬 집중 통계(`scope=island`) | 12,067–12,381B |
| 섬 메시지 목록 | 8,066–9,541B |
| 섬 집중 통계(`scope=me`) | 5,881–5,896B |
| `/screens/home` | 3,842–3,878B |
| `/rankings/islands` | 3,648B |
| `/screens/library` | 2,508–3,177B |

같은 경로가 여러 시나리오에 반복돼 중복이 있다. 운영 트래픽으로 가중한 값이 아니므로 32.3%를 전체 요청의 압축 적용률로, 88.8%를 전체 트래픽 절감률로 읽지 않는다. Realtime 채팅 메시지 응답(8,806–10,371B)은 이번 변경으로 압축되지 않는다.

### 저장 본문의 로컬 gzip

| 응답 | 원본 크기 | 로컬 gzip 크기 | 표본 합계 기준 절감 |
| --- | ---: | ---: | ---: |
| `/islands` 첫 페이지(3개) | 8,130–8,131B | 1,258–1,277B | 84.4% |
| `/islands` 다음 페이지(3개) | 3,870B | 629B | 83.7% |
| `/me/telescope`(3개) | 1,994–1,996B | 497–508B | 74.9% |

- `/me/telescope`는 압축은 잘되지만 2,048B 미만이라 이번 설정에서는 압축하지 않는다.
- 로컬 Python gzip 결과다. Tomcat 출력이나 Cloudflare를 거쳐 앱에 온 바이트와 같다고 가정하지 않는다. 본문이 보관되지 않은 메일함·통계 응답에 이 비율을 대입하지 않는다.

### 검증과 미측정

- `ResponseCompressionTest`가 로컬 Tomcat에서 2,047B JSON은 원본, 2,048B JSON은 gzip임을 확인한다. 해제 후 본문 일치, `Accept-Encoding: identity`의 비압축, `Vary` 헤더, 4,096B PNG 비압축도 확인한다. Business API 테스트 331개와 정적 검사가 통과했다. 운영 API 요청은 포함하지 않았다.
- 미측정: 실제 앱 요청의 `Accept-Encoding`, 운영 Cloudflare가 이미 적용하는 압축, 최종 수신 바이트, 응답 시간 변화, 오리진 CPU 비용.
- 후속 확인은 이미 수집된 헤더·로그·메트릭의 읽기 전용 분석이나 AWS에 요청하지 않는 로컬 환경으로 한다. 운영 부하 재측정은 하지 않는다.
